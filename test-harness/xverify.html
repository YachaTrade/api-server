X Hidden Creator Launch — Manual Test Harness

Single-file, no-build dev tool. Talks directly to a locally running api-server. Throwaway — not production UI.

0. Instructions

  1. Serve this file so the browser's Origin header is allowed by the API's CORS/CSRF allowlist. Confirmed by reading src/cors.rs (is_origin_allowed) and src/middleware.rs (is_allowed_origin, used by the authenticate_user CSRF check): both allow any origin starting with http://localhost: (any port), plus a few fixed production/staging domains. This is not env-driven — it's a hardcoded allowlist in source. So serve this directory over plain HTTP on localhost, any port, e.g.: 
    cd test-harness
python3 -m http.server 5500
# then open http://localhost:5500/xverify.html
    Do not open this file via file:// — there is no Origin header at all in that case for cross-origin fetches, and some browsers behave inconsistently. A real http://localhost:<port> origin is required.
  2. Server-side env vars for the OAuth round trip (read from src/config.rs, both are .expect(...) — the server will not boot without them): X_OAUTH_REDIRECT_SUCCESS_URL and X_OAUTH_REDIRECT_FAILURE_URL. Point both back at wherever you're serving this page, e.g. (matching the port above): 
    X_OAUTH_REDIRECT_SUCCESS_URL=http://localhost:5500/xverify.html?x_verified=1
X_OAUTH_REDIRECT_FAILURE_URL=http://localhost:5500/xverify.html
    GET /x/oauth/callback (in src/router/x_verification/handler.rs) always 302-redirects the browser to one of these two FIXED server-configured URLs (never anything client-supplied) — on failure it appends ?x_verify_error=<code> (or &x_verify_error=... if the failure URL already has a ?). Real codes emitted by oauth_callback: denied (X returned an error param), bad_request (missing code/state), state_expired (AppError::Gone), x_error (any other failure). This page parses window.location.search for x_verify_error on load and shows it in the red banner above.
  3. Click-through order: (1) set Base URL, (2) Connect Wallet (SIWE-style login), (3) Verify with X (full navigation away and back), (4) Refresh Pending, (5) Add Followed-By handle(s), (6) Mine Salt, (7) Reserve, (8) Finalize, (9) Check xinfo.
  4. Also confirmed while reading the auth code (src/services/auth/mod.rs): the POST /auth/session cookie is set with Secure; SameSite=None. Chrome/Edge treat http://localhost as a secure context so this generally still works; Safari/Firefox may refuse to store it. Use Chrome/Edge for this tool if login appears to succeed but subsequent authed calls 401.
  5. This tool intentionally stops after finalize/xinfo — it performs no on-chain contract calls. Because nothing is ever actually deployed at the mined address, reserve's "not yet deployed" on-chain check (in services/x_verification) will naturally pass every time you run this flow.
