# Nad.fun Api 서버 아키텍처 명세서

## 개요

NADS Pump은 탈중앙화 거래 플랫폼을 위해 설계된 고성능 Rust 기반 API 서버입니다. 이 아키텍처는 암호화폐/DeFi 애플리케이션에 적합한 확장성, 실시간 성능, 그리고 견고성을 강조합니다.

## 기술 스택

### 핵심 기술

- **프로그래밍 언어**: Rust (2021 Edition)
- **웹 프레임워크**: Axum 0.7.5
- **비동기 런타임**: Tokio 1.38.0
- **데이터베이스 ORM**: SQLx 0.8.1 (컴파일 타임 쿼리 검증)
- **API 문서화**: Utoipa (OpenAPI/Swagger)

### 데이터 저장소

- **주 데이터베이스**: PostgreSQL with PgBouncer 연결 풀링
- **캐시 레이어**: Redis with deadpool 연결 관리
- **객체 저장소**: AWS S3 파일 저장

### 블록체인 통합

- **Web3 라이브러리**: Alloy 0.11.0 (이더리움 상호작용)
- **지원 네트워크**: EVM 호환 체인

## 핵심 컴포넌트

### 1. 애플리케이션 상태 관리

```rust
pub struct AppState {
    pub postgres: Arc<PostgresDatabase>,
    pub session_redis: Arc<RedisDatabase>,
    pub trade_redis: Arc<RedisDatabase>,
    pub s3_client: Arc<S3Client>,
}
```

애플리케이션 상태의 특징:

- 시작 시 한 번만 생성
- 각 요청마다 복제 (Arc 참조)
- 스레드 안전하고 불변
- 모든 공유 리소스에 대한 접근 제공

### 2. 요청 처리 파이프라인

1. **요청 수신**: Axum 서버가 HTTP 요청 수신
2. **미들웨어 처리** (순서대로):
   - 속도 제한 (Governor - 현재 비활성화)
   - 쿠키 관리
   - CORS 검증
   - 타임아웃 적용 (10초)
   - 인증 (보호된 라우트의 경우)
3. **라우트 처리**: 적절한 핸들러로 요청 라우팅
4. **비즈니스 로직**: 핸들러가 컨트롤러를 사용해 요청 처리
5. **응답 생성**: 데이터 직렬화 및 반환

### 3. 에러 처리 아키텍처

```rust
pub enum AppError {
    BadRequest(String),
    Unauthorized(String),
    Forbidden(String),
    NotFound(String),
    InternalServerError(String),
    ServiceUnavailable(String),
}
```

- HTTP 응답으로 자동 변환
- API 전체에서 일관된 에러 형식
- 디버깅을 위한 상세한 에러 메시지
- 클라이언트에게 안전한 에러 메시지

### 모듈 설계 원칙

1. **독립적인 기능**: 각 라우터 모듈은 다음을 포함:

   - `mod.rs`: 모듈 익스포트 및 라우터 설정
   - `handler.rs`: HTTP 요청 핸들러
   - `path.rs`: 라우트 경로 정의

2. **공유 타입**: 모듈 간 사용을 위한 `types/common/`의 공통 타입

3. **컨트롤러 패턴**: 비즈니스 로직을 컨트롤러 타입으로 캡슐화

## 데이터 레이어 아키텍처

### 데이터베이스 스키마 설계

데이터베이스는 성능을 위한 전략적 비정규화와 함께 정규화된 관계형 설계를 따릅니다:

### PostgreSQL 아키텍처

#### 연결 풀링

```rust
쓰기 풀: 최대 50개 연결, 최소 5개 연결
읽기 풀: 최대 1000개 연결, 최소 10개 연결
```

- **읽기/쓰기 분리**: 주 DB와 복제본을 위한 별도의 풀
- **PgBouncer 최적화**: 트랜잭션 풀링 모드
- **문장 캐싱**: 1000개(쓰기) / 2000개(읽기) 캐시된 문장

#### 인덱싱 전략

1. **기본 인덱스**: 모든 외래 키와 기본 키
2. **복합 인덱스**: 일반적인 쿼리 패턴용
3. **부분 인덱스**: 필터링된 쿼리용

### Redis 아키텍처

#### 이중 Redis 설계

1. **세션 Redis**: 인증 및 세션 데이터
2. **거래 Redis**: 시장 데이터 및 거래 캐시

#### 캐싱 전략

```
캐시 키 패턴:
- token:{token_id}
- order:{order_type}:response:page:{page}_limit:{limit}
- search:tokens:query:{query}:page:{page}:limit:{limit}
```

#### TTL 설정

- 세션 데이터: 24시간
- 로그인 메시지: 3분
- 시장 데이터: 1.5초
- 차트 데이터: 5-300초 (간격에 따라)

## 타입 시스템 설계

### 설계 원칙

1. **강타입**: 동적 타입의 최소 사용
2. **컴파일 타임 안전성**: 컴파일 시점의 SQLx 쿼리 검증
3. **도메인 모델링**: 비즈니스 도메인과 밀접하게 일치하는 타입

3. **도메인 타입**: 비즈니스 로직 엔티티
4. **공통 타입**: 모듈 간 공유

## 보안 아키텍처

### 인증 플로우

1. **SIWE (이더리움으로 로그인)**:

   - 논스 생성 및 저장
   - 메시지 서명 검증
   - 쿠키를 통한 세션 생성

2. **세션 관리**:

   - Redis 기반 세션
   - 24시간 TTL
   - 쿠키 기반 인증

3. **미들웨어 보호**:
   - 선택적 라우트 보호
   - 요청 확장에 사용자 주입

### 보안 조치

1. **CORS 설정**: 환경 기반 원본 검증
2. **속도 제한**: Governor를 통한 설정 (현재 비활성화)
3. **SQL 인젝션 방지**: SQLx를 통한 준비된 문장
4. **입력 검증**: 강타입 및 serde 검증
5. **타임아웃 보호**: 10초 요청 타임아웃

1. **다단계 캐싱**:
